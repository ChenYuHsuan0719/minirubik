## The state space

### The group $\langle R, B, D \rangle$ and its order

#### Group definition
* The group is generated by the three face turns R, B, D.
* A group needs closure, an identity element and an inverse for every element. Doing nothing is the identity, and every turn can be undone (R' undoes R).
* A real cube also has U, F, L, but they are not needed. Because of closure, a combination of turns is still a turn: for example L is the same as R plus a rotation of the whole cube. So R, B, D are enough once we stop counting whole-cube rotations.

#### Fixing one corner
* Without turning any face, a cube can be held in 24 different ways, so every state would be counted 24 times.
* Fixing one corner (corner 0, front-upper-left) decides how the cube is held. R, B, D never move this corner.
* Check: without fixing a corner there are $8! \cdot 3^7$ arrangements; divided by 24 this gives 3,674,160 $= 7! \cdot 3^6$.

#### Order
* Permutation: 8 corners, one is fixed, so 7 corners in 7 places: $7! = 5040$.
* Orientation: each corner can be twisted 3 ways, but the last twist is decided by the other six (see the invariant below): $3^6 = 729$.
* Total: $7! \cdot 3^6 = 3{,}674{,}160$ states.

### Cayley graph and generators

#### Cayley graph definition
* Let $G$ be a group and $S$ a generating set. The Cayley graph is $\Gamma = \Gamma(G, S)$.
* Vertex set: one vertex per group element, $V = G$. Here each vertex is one cube state, so there are 3,674,160 vertices.
* Edge set: for $g, h \in G$, there is an edge labeled $s$ from $g$ to $h$ if $h = gs$ for some $s \in S$. In words: if applying one move to state 1 gives state 2, the two states are connected.

#### Generators
* A generating set is a set of elements whose products (and inverses) give every element of the group.
* The solver uses 9 generators: R, R2, R', B, B2, B', D, D2, D'.
* Every state has 9 outgoing edges, so there are $3{,}674{,}160 \times 9 = 33{,}067{,}440$ directed edges. The set is closed under inverse, so the graph can be treated as undirected.

#### Shortest solution = shortest path
* The fewest moves that solve a state is the length of the shortest path from that vertex to the solved vertex. Since every edge has weight 1, BFS finds it.

#### HTM vs. QTM
* The difference is the generator set. This assignment uses HTM.
* HTM (half-turn metric): R2 counts as one move. 9 generators.
* QTM (quarter-turn metric): R2 is two moves (R R). Only 6 generators.

### Diameter 11 by exhaustive BFS

#### BFS
BFS starts from the solved state and visits states layer by layer. Every state in layer $k$ is first reached from layer $k-1$, so its distance is exactly $k$. The diameter is the index of the last non-empty layer.

### The orientation-sum invariant
* Every reachable state satisfies $\sum_i o_i \equiv 0 \pmod 3$.
* Why it holds: in `twist[]`, each quarter turn adds 1, 2, 1, 2 to the four corners it moves (R: twists 1, 2, 2, 1; B: 1, 2, 1, 2; D: all 0). The sum of added twists is 6 or 0, which is $\equiv 0 \pmod 3$. So no turn changes the sum mod 3, and the solved state starts at 0.
* What it rules out: a cube with a single twisted corner. Only one third of the $3^7$ orientation patterns are reachable, which is why the 7th orientation is not stored.
* Why mod 3 and not parity: a corner has three orientations, so the twist group is $\mathbb{Z}_3$, not $\mathbb{Z}_2$. Parity is the rule for 2-state pieces like edges on a 3×3 cube.

## Stage 1: Characterize the baseline

### What `solver.c` computes
* `build_table` runs BFS from the solved state over all 3,674,160 states. For each state it stores one byte: the move that goes one step toward solved (the inverse of the move that first reached it).
* A query parses the input, ranks it, then repeatedly looks up the table, applies the stored move, and re-ranks until it reaches rank 0.
* The answer is optimal: each stored move goes from layer $k$ to layer $k-1$, so following them takes exactly $k$ moves, which is the BFS distance.

### How a cube is represented

```text
0 : Fix

                UP
                ┌───┬───┐
                │ 7 │ 4 │
                ├───┼───┤
                │ 0 │ 1 │
                └───┴───┘

  LEFT         FRONT         RIGHT         BACK
┌───┬───┐     ┌───┬───┐     ┌───┬───┐     ┌───┬───┐
│ 7 │ 0 │     │ 0 │ 1 │     │ 1 │ 4 │     │ 4 │ 7 │
├───┼───┤     ├───┼───┤     ├───┼───┤     ├───┼───┤
│ 6 │ 3 │     │ 3 │ 2 │     │ 2 │ 5 │     │ 5 │ 6 │
└───┴───┘     └───┴───┘     └───┴───┘     └───┴───┘

                DOWN
                ┌───┬───┐
                │ 3 │ 2 │
                ├───┼───┤
                │ 6 │ 5 │
                └───┴───┘
```

* `state_t` holds `p[7]` (which cubie is in each slot) and `o[7]` (its twist, 0..2).
* `rank_state` turns a state into one integer in $[0, 3674160)$:
  * Permutation: Lehmer code. For each slot $i$, count how many later cubies are smaller, then `p = p * (7 - i) + smaller`. This gives 0..5039.
  * Orientation: read `o[0..5]` as a base-3 number, 0..728. `o[6]` is not stored because the invariant decides it.
  * `rank = p * 729 + o`.
* `unrank_state` is the inverse, so `rank` is a bijection (checked by `--self-test` for all states).

#### Important constants
* `CUBIES = 7`
* `PERMUTATIONS = 5040 = 7!`
* `ORIENTATIONS = 729 = 3^6`
* `STATES = PERMUTATIONS * ORIENTATIONS = 3,674,160`
* `MOVES = 9` = 3 faces × 3 turn amounts

#### Faces and viewpoint
* R (0): seen from the right side of the cube.
* B (1): seen from behind the cube.
* D (2): seen from below the cube.

#### Move index
* R (0): right face clockwise 90°; R2 (1): 180°; R' (2): 270° = counter-clockwise 90°.
* B (3), B2 (4), B' (5): same for the back face.
* D (6), D2 (7), D' (8): same for the down face.
* `face = move / 3`, `turns = move % 3 + 1`. Only the quarter turn is coded; R2 and R' are R applied 2 or 3 times.

#### `source` and `twist`
* Index = destination slot, value = source slot.
* Size `[3][CUBIES]`, one row per face. Both are hard-coded constants.

```c
static const uint8_t source[3][CUBIES] = {
    {1, 4, 2, 0, 3, 5, 6},     // R
    {0, 1, 2, 4, 5, 6, 3},     // B
    {0, 2, 5, 3, 1, 4, 6},     // D
};
static const uint8_t twist[3][CUBIES] = {
    {1, 2, 0, 2, 1, 0, 0},     // R
    {0, 0, 0, 1, 2, 1, 2},     // B
    {0, 0, 0, 0, 0, 0, 0},     // D
};
```

A quarter turn does `result.p[i] = state.p[source[f][i]]` and `result.o[i] = (state.o[source[f][i]] + twist[f][i]) % 3`.

### Invariants the program relies on
* Fixed corner: R, B, D never move corner 0, so whole-cube rotations never appear.
* Orientation sum $\equiv 0 \pmod 3$: lets the program drop `o[6]` and reject impossible inputs in `valid()`.
* Permutation and orientation move independently: the new permutation depends only on the old permutation, and the new orientation only on the old orientation. So `build_table` can use two small transition tables (`permutation[3][5040]`, `orientation[3][729]`) instead of one table over all states.
* `rank` is a bijection: every state has exactly one table slot.

* Instruction estimate : BFS visits 3,674,160 states × 9 moves = about $3.3 \times 10^7$ transition updates. Each update does two table loads, one multiply-add to rebuild the rank, one byte load to test "visited", and sometimes two stores, so roughly 10–20 instructions. That gives about $10^8$ to $10^9$ instructions. On RV32I the `* 729`, `/ 729` and `% 729` have no hardware instruction and become software routines, so the real count is at the high end.

### Measurement 1: host bytes per guest byte
Method: a tight store loop that writes N bytes, compared with N = 0 as control. I measure Ripes' max RSS (`measure/memfill.sh`).

#### What VSRTL's source predicts
```cpp
std::unordered_map<VSRTL_VT_U, uint8_t> m_data;
```
* `unordered_map` is a C++ hash map. The key is the address, the value is one byte.
* Every new guest byte becomes one hash node (key, value, next pointer, malloc header) plus a bucket slot, so I expected tens of host bytes per guest byte.

#### Results
| Guest bytes written | Max RSS (KiB) | Δ vs. control (KiB) |
| ---: | ---: | ---: |
| 0 (control) | 33332 | - |
| 1 MiB | 77000 | 43668 |
| 4 MiB | 210844 | 177512 |
| 16 MiB | 749464 | 716132 |

* Max RSS: the largest amount of real RAM the process used.
* Δ vs. control $= \text{MaxRSS}_N - \text{MaxRSS}_0$.

#### Slope
* Host byte: memory Ripes uses on the real machine to remember one guest byte.
* Guest byte: one byte written by the RISC-V program (`sw` writes 4).
* Slope $= (\text{RSS}_{16M} - \text{RSS}_{4M}) \times 1024 \div (16777216 - 4194304) \approx 43.8$.
* Projection for the 18,405,414-byte baseline peak: $43.8 \times 18{,}405{,}414 \approx 807$ MB.
* So each guest byte costs about 44 host bytes, matching the hash-map prediction. 18 MB of guest data becomes about 800 MB in Ripes.

### Why the full table does not survive the move to Ripes
report.md §7 argues that the full table is fine because it is built once and is useful as a verification artifact. On a normal computer this is true: 18 MB and a fraction of a second are nothing.

In Ripes it fails:
* Memory: 18 MB of guest data costs about 800 MB of host RAM (Measurement 1), and it is far above the 128 KiB static-data limit.
* Time: about $10^9$ instructions take minutes on `RV32_ISS` and hours on the pipeline models (Measurement 2).
* RV32I has no `mul`/`div`, so ranking with `* 729` and `/ 729` costs even more.

The verification role does not need Ripes. I keep the full BFS on the host as the reference answer (gates H1–H3) and only run a small search on the target. This leads to Stage 2.

## Stage 2: Representation and algorithm for the target

### Constraints carried over from Stage 1
1. Static data (`.data` + `.rodata` + `.bss`) under 128 KiB → no full table; only small lookup tables.
2. No distance-11 state may exceed $5 \times 10^7$ retired instructions on `RV32_ISS` → the search needs a strong heuristic.
3. RV32I only, no `mul`/`div` → no `/` or `%` in the hot loop; use lookup tables.
4. No heap, no recursion, no float → fixed-size arrays; an iterative search with an explicit stack.

### Search algorithm: IDA*
* IDA* is depth-first search with a cost limit `bound`. A node is cut when $f = g + h > \text{bound}$, where $g$ is the depth and $h$ is the heuristic.
* No queue: memory is one array entry per depth, at most 12 levels. BFS or A* would need a queue as large as the state space.
* `bound` starts at $h(\text{root})$, the smallest possible answer. After each round it becomes the smallest $f$ that was cut.
* Optimal: $h$ never overestimates, so a solution of length $L$ is never cut while $\text{bound} \ge L$, and bound grows through every possible value in order. The first solution found is the shortest.
* Terminates: every state is at most 11 away, so bound never needs to pass 11.
* My version is iterative: the arrays `sp/so` (state at depth d), `cp/co` (current child), `next[d]` (next move to try) and `last_face[d]` replace the recursion.

### Heuristic and abstractions
* Pattern database (PDB): ignore part of the state, BFS the small abstract space, and store the exact distance there. Any real solution is also a solution in the abstract space, so the PDB distance is a lower bound (admissible).
* This works because permutation and orientation move independently (Stage 1 invariant).
* Two PDBs: `pdb_p[5040]` (permutation only) and `pdb_o[729]` (orientation only).
* `h(s) = max(pdb_p[p], pdb_o[o])`. The max of two lower bounds is still a lower bound.
* The tables are computed on the host by `gen_table.c` and written into `tables.h` / `tables.s` as constant arrays.

### Pruning

The search cuts two different kinds of branches.

#### 1. Same face twice in a row (redundant move sequences)
* R + R2 = three quarter turns = R'
* R + R' = back to the original state
* R2 + R2 = back to the original state
* So any sequence that turns the same face twice in a row can be replaced by a shorter one, and it can never be a shortest solution. The search skips all three moves of the last face:
  ```c
  if (face == last_face[d]) {
      next[d] = (uint8_t) (move + 3U);   // skip X, X2, X' of this face
      continue;
  }
  ```
* This cuts the branching factor from 9 to 6 after the first move.
* Measured on `21345671111111`: 298,839 nodes without this pruning, 38,998 nodes with it (7.7× fewer).
* Not applicable here: 3×3 solvers also fix the order of opposite faces (R L = L R). R, B and D all touch the fixed corner 0, so no two of them are opposite and they do not commute. There is no second sequence rule to add.

#### 2. $f > \text{bound}$ (heuristic pruning)
* For a child at depth $d + 1$, the search computes $f = (d + 1) + h(\text{child})$:
  ```c
  uint8_t f = (uint8_t) (d + 1U + heuristic(cp[d], co[d]));
  if (f > bound) { if (f < min) min = f; continue; }
  ```
* $d + 1$ moves are already used, and $h$ says at least $h$ more are needed. If the sum is above `bound`, no solution of length `bound` goes through this child, so its whole subtree is skipped in this round.
* The smallest cut $f$ is kept in `min` and becomes the next `bound`.
* This never removes a shortest solution because $h$ never overestimates (gate H1). A stronger $h$ cuts more.

| | Same-face pruning | $f > \text{bound}$ |
| :--- | :--- | :--- |
| What is cut | redundant move sequences | subtrees that cannot finish within `bound` |
| Based on | group property, e.g. R · R2 = R' | lower bound from the PDBs |
| Why no solution is lost | a cut sequence always has a shorter equivalent | $h(s) \le d(s)$ (H1) |

## Stage 3: Efficiency in C

### Estimate the number of instructions required to run IDA* on Ripes (roughly)

$$\text{retired instructions} \approx \text{children generated} \times \text{instructions per child} + \text{nodes expanded} \times \text{instructions per node}$$

* An optimization either generates fewer children (better pruning, stronger $h$) or makes each child cheaper (fewer loads, no `div`/`mul`). 
* A "child" is one move that is actually applied and evaluated with $h$. 
* A "node" is a child that passes the bound and is expanded.
* The average number of instructions required to process a child node primarily involves:

    1. Applying a move: looking up the move table and updating the permutation (CP) and orientation (CO) of the corner pieces.
    2. Calculating *h*: converting the state into an index and querying the Pattern Database (PDB).
    3. Comparing *g* + *h* against the bound to decide whether to prune or retain the node.

### Steps

| Step | Change | Nodes (`21345671111111`) | Worst distance-11 state: nodes / children | Est. RV32I instructions, worst case |
| :--- | :--- | ---: | ---: | ---: |
| 0 | IDA* + max(pdb_p, pdb_o), no same-face pruning | 298,839 | - | - |
| 1 | skip same face twice in a row | 38,998 | 106,635 / 639,793 | - |
| 2 | X, X2, X' reuse the previous child | 38,998 | same | - |
| 3 | `move / 3`, `move % 3` → `move_face[]`, `move_turn[]` | 38,998 | same | - |
| 4 | recursion → fixed arrays | 38,998 | same | ≈ 37 M |
| 5 | bigger PDB: $h = \max(\text{big}[p \cdot 27 + o_{0..2}], \text{pdb\_o}[o])$, 4-bit packed | **2,761** | **9,682 / 58,077** | **≈ 4 M** |

Mean over all 2,644 distance-11 states: 34,439 nodes (step 4) → 2,805 nodes (step 5).

### Instructions per child (hand count)

I wrote out the RV32I sequence for one child, with the table base addresses kept in registers:

| Part | Instructions |
| :--- | ---: |
| load `next[d]`, test `== 9`, store `next[d] + 1` | 6 |
| `move_face[move]`, compare with `last_face[d]` | 5 |
| `move_turn[move]`, pick `sp/so` or `cp/co` | 8 |
| `perm_move[face][np]` (base from `perm_tab`, `slli`, `add`, `lhu`) | 6 |
| `ori_move[face][no]` | 6 |
| store `cp[d]`, `co[d]` | 5 |
| `pdb_p`, `pdb_o`, max | 6 |
| $f = d + 1 + h$, compare with bound, update `min` | 6 |
| Total | ≈ 50 |

Per expanded node about 20 more (store `sp`, `so`, `last_face`, `next`, `path`, `d + 1`, plus backtracking). Step 5 adds about 12 per child: `p * 27` as shift-and-add (`(p << 5) - (p << 2) - p`), one `lbu` for `grp[o]`, and the nibble read (`srli`, `add`, `lbu`, test the low bit, shift or mask).

* Step 4 estimate: 639,793 × 55 + 106,635 × 20 ≈ 37 M. Under the $5 \times 10^7$ limit, but only by about 25%.
* Step 5 estimate: 58,077 × 67 + 9,682 × 20 ≈ 4.1 M. About 12× below the limit.
* At the Measurement 2 rates, 4 M instructions is about 1.4 s on `RV32_ISS` and about 25 s on `RV32_5S` (37 M would be 13 s and 3.8 min).

These are estimates. Measured in Ripes (Stage 4), `solver.s` needs about 72 instructions per child including node work (16,942,891 / 233,962 on the sample), and the worst distance-11 state takes 46.3 M, more than the 37 M estimate. The difference is that `solver.s` reloads every array base address with `la` (2 instructions) inside the loop, while the hand count assumed the bases stay in registers.

### Why each step helps

* **Step 1** (fewer children): after the first move only 6 of 9 moves are tried. 298,839 → 38,998 nodes on the sample (7.7×). See Stage 2, Pruning.
* **Step 2** (cheaper child): X2 is one more quarter turn on the X child, X' one more on X2. A face costs 3 lookup pairs instead of 1 + 2 + 3 = 6, which saves about 12 instructions per child (~20%).
* **Step 3** (cheaper child): RV32I has no `div`/`rem`. `move / 3` and `move % 3` would each call a software divide (a shift-and-subtract loop of up to 32 iterations, on the order of 100 instructions). A table lookup is `add` + `lbu`, 2 instructions.
* **Step 4** (required): the rules forbid recursion. Each recursive call would also save and restore `ra` and the callee-saved registers; the explicit arrays only store what is needed per level.
* **No multiply in the search**: the state is kept as two ranks `(p, o)` instead of `p * 729 + o`, so the hot loop never multiplies.
* **Step 5** (fewer children): the PDB keeps the full permutation plus the orientation of slots 0..2 (`o / 27`, 27 values): 5040 × 27 = 136,080 entries. Each entry is the minimum true distance over all states that project to it, computed on the host from the full BFS, so it is a lower bound by construction (H1 and H3 re-checked for all 3,674,160 states). Its values are larger than `pdb_p` (most are 6–8 instead of 4–6), so the bound starts closer to the real distance and far fewer subtrees survive: 11× fewer children in the worst case.

| :--- | ---: |

`pdb_p` is no longer needed: every `big` entry with permutation $p$ is at least `pdb_p[p]`, so `big` dominates it.

## Stage 4: RV32I assembly

Status: `solver.s` (v1) runs in Ripes and matches the host solver. It is a direct translation of the step-4 C version: IDA* with $h = \max(\text{pdb\_p}, \text{pdb\_o})$, not yet the step-5 PDB.

### Program structure
* `gen_table --asm` writes `tables.s` (all tables as `.half` / `.byte`); it is concatenated before `solver.s` because Ripes needs labels defined before `.word` uses them.
* The input string is inlined as `input: .string "21345671111111"` since Ripes has no command line.
* `perm_tab` / `ori_tab` hold the addresses of the three per-face tables, selected with `slli face, 2` + `lw`.
* IDA* arrays (`sp_arr`, `so_arr`, `cp_arr`, `co_arr`, `last_face`, `next_mv`, `path`) are in `.data`, fixed size 12.
* Output: `ecall 11` per character.

### Key instruction sequences
* `o * 3` without `mul`: `slli t, o, 1; add o, t, o`.
* `sum % 3` for the input check: subtract 3 in a loop (the sum is at most 14).
* Table lookup `perm_move[face][np]`: `lw` the table base, `slli np, 1`, `add`, `lhu`.

## Results that did not pay
* Steps 2–4 of Stage 3 do not change the node count; they only make each child cheaper. Their gain is an estimate until the assembly runs.
* The step-5 PDB stored as one byte per entry is 136,080 bytes, over the 131,072-byte limit on its own. It only fits with 4-bit packing, which costs about 5 extra instructions per lookup. Packing pays here because it is the only way to fit the table that cuts the children by 11×.
